SAM × AFAB 비교 시스템 매뉴얼

WINGS 주문 데이터와 SAM 내부견적서(.docx)의 옵션 코드를 자동 대조하여 누락·불일치·필수코드 미반영을 찾아내는 시스템의 전체 로직을 설명합니다. 대상: 운영 관리자 및 유지보수 개발자.

1. 개요 & 아키텍처

핵심 원리 한 줄: "계산도 표시도 브라우저에서, 데이터는 SharePoint에서."

이 시스템은 두 개의 서로 다른 데이터 소스를 비교합니다.

WINGS 주문 시스템 export

차량 1대(=Commission no.) 당 실제 주문된 옵션 코드 목록. CSV/Excel로 내려받은 파일. "실제로 이렇게 주문됐다"는 사실(fact).

SAM 내부 견적서(.docx)

모델별 표준 견적서. 그 모델이 "이런 코드 구성이어야 한다"는 기준(reference). Word 문서에서 장비표·도장·타이어를 파싱.

비교 결과는 차량 한 대마다 세 가지 상태 중 하나로 분류됩니다.

Match SAM 파일을 찾았고 차이가 없음  ·  Mismatch SAM을 찾았으나 코드/도장/타이어가 다름  ·  No SAM 비교할 SAM 파일 자체가 없음

계산은 관리자가 [⟳ 데이터 빌드]를 누른 브라우저에서 한 번만 일어납니다. 파싱·모델 매칭·비교가 끝나면 결과 data.json·codes.json이 SharePoint 05. output에 저장되고, 다른 사용자는 그 결과만 읽습니다(재계산 없음). 서버·GitHub Actions·클라이언트 시크릿·PAT는 사용하지 않습니다.

왜 이 구조인가 — 해결한 4가지 문제

문제해결 방법
.docx 파싱내장 ZIP 리더(lib/unzip.js)+정규식 파서로 브라우저에서 직접 파싱 (외부 라이브러리 불필요)
토큰/자격증명 보안시크릿·PAT이 아예 없음 — 로그인 사용자의 위임 Graph 토큰(MSAL)만 사용
계산 부하빌드는 관리자 1인의 브라우저에서 1회 → 나머지 사용자는 저장된 JSON만 로드
WINGS 데이터 취득SharePoint에서 매 빌드마다 최신 파일을 새로 내려받음

2. 데이터 소스 — SharePoint

원본 데이터는 저장소(repo)에 커밋하지 않고 SharePoint 문서 라이브러리에만 둡니다. 빌드는 실행할 때마다 앱 전용 Graph API로 새로 내려받습니다.

사이트: startruckkorea.sharepoint.com/sites/SAM-AFAB · 기본 라이브러리 "Shared Documents"

폴더내용빌드가 사용하는 범위
01. SAM_filesSAM 원본 .docx (월별 YYYY-MM 하위폴더)가장 최근 생산월 폴더만
02. WINGS_dataWINGS export (xlsx/csv)가장 최신 파일 1개만
03. model_rulesmodel_mapping.xlsx — 모든 모델 매칭 규칙전체
04. code코드 사전 / 필수코드 / 카테고리 / cab xlsx전체

최신 파일 선택 규칙 lib/pipeline.js build_data.py

"최신"은 파일 수정시각(mtime)이 아니라 파일명에 박힌 타임스탬프를 우선합니다 (복사/다운로드 시 mtime이 바뀌기 때문). 우선순위:

  1. 파일명 끝의 13자리 epoch-ms (예: ..._1783469227544)
  2. 파일명 속 날짜 YYYY-MM-DD / YYYYMMDD
  3. 둘 다 없으면 파일 수정시각(mtime)

SAM 월 폴더는 폴더명 YYYY-MM을 정수 YYYYMM으로 바꿔 최댓값을 최신 월로 봅니다.

출력 data.json은 { generated_at, wings_file, columns, summary, rows[] } 구조. summary는 total·matched·mismatched·no_sam·sam_months 집계.

4. WINGS 파싱 로직 backend/wings_parser.py

목표: 형식이 조금씩 다른 WINGS export를 일관된 DataFrame으로 정규화. 차량 1대 = 1행.

4.1 컬럼 자동 인식

파일마다 컬럼 이름/순서가 다를 수 있어, 이름 패턴으로 유연하게 찾습니다.

대상인식 우선순위
모델명Type (brief) → Type → Baumuster → 2번째 컬럼
옵션 코드①이름에 standard+equipment 포함 컬럼
옵션 코드②이름에 additional+equipment 포함 컬럼
(대체)못 찾으면 9번째·11번째 컬럼, 그래도 없으면 equipment/offer code/enumeration 포함 컬럼
도장Paint zone N color code
타이어Tyre key N. axle + Tyre manufacturer key N. axle

4.2 코드 추출

선택된 옵션 컬럼들의 텍스트를 합쳐 정규식으로 코드를 뽑습니다.

return set(re.findall(r"\b[A-Z0-9]{3,5}\b", text.upper()))

왜 3~5자인가? 현재 옵션 코드는 3~4자지만, Additional equipment에 나오는 4~5자 CTT 코드가 옛 {3,4} 패턴에서 앞 4자로 잘려나가던 문제가 있었습니다. 상한을 5로 늘려 긴 코드를 온전히 보존합니다(3~4자 코드에는 무영향). nan 문자열은 미리 제거합니다.

PTO 플래그는 합친 텍스트에 \bPTO\b가 있으면 WINGS_has_pto = True.

4.3 도장(Paint) 정규화

WINGS 셀은 4자리 MB 색상번호(예: 9676, Excel에서 9676.0으로 읽힐 수 있음). 소수점 꼬리를 떼고 3~5자리 숫자만 추출해 SAM의 MB 9676과 맞춥니다.

4.4 타이어(Tyre) 정규화 — 축(axle)별 페어링

타이어는 두 컬럼을 축 번호로 짝지어 합칩니다.

  • Tyre key N. axle → 6자 키(예: F18L96)
  • Tyre manufacturer key N. axle → 2자리 제조/하중지수(예: 81)
  • 같은 축의 둘을 합쳐 "F18L96 81" — SAM 타이어 라인의 형식과 일치

결과 컬럼: WINGS_codes, WINGS_has_pto, WINGS_paint, WINGS_tyre, 그리고 존재 시 Order status, FIN, Subcategory (ID), Vehicle alterable until, Requested delivery date 등.

5. SAM 파싱 로직 backend/sam_parser.py

목표: 각 .docx를 {정규화모델: {PTO여부: [후보 데이터,…]}} 맵으로 변환. .docx는 zip이며 word/document.xml을 XML로 직접 파싱합니다(외부 Word 라이브러리 없음).

5.1 장비 코드 추출 — 표 → 섹션 → 셀

a

대상 표 선택

문서 내 모든 표를 훑어 텍스트에 "Equipment overview"가 있는 표를 우선, 없으면 "Standard equipment" 표를 대체로 씁니다.

b

섹션 상태머신

표 안 문단을 순회하며 STANDARD/SPECIAL/ADDITIONAL EQUIPMENT 헤더를 만나면 "현재 섹션"을 바꿉니다.

c

섹션별 코드 규칙

  • STANDARD / SPECIAL: 문단에서 \b[A-Z][A-Z0-9]{2,3}\b 모두 수집
  • ADDITIONAL: 문단 맨 앞 토큰 1개만(설명문에 낀 대문자 오탐 방지)

가짜 코드 걸러내기

느슨한 정규식이 CTT 같은 산문 단어도 잡을 수 있습니다. 그래서 최종적으로 숫자를 포함한 토큰은 그대로 인정하되, 전부 영문인 토큰은 실제 SA 코드 사전(OPTION_CODE_MAP ∪ 필수코드)에 있을 때만 남깁니다.

codes = {c for c in codes
         if any(ch.isdigit() for ch in c) or c in KNOWN_CODES}

5.2 도장/타이어 추출

장비표와 별개로, 본문에서 Paint/Tyres 섹션을 상태머신으로 추적합니다.

  • 도장: MB\s*(\d{4}) → 9676
  • 타이어: ...R 22,5F18L96 81738.00에서 6자 키 + 뒤 2자리 지수 → F18L96 81 (지수가 가격과 붙어있어 공백 뒤 정확히 2자리만 취함)

5.3 두 개의 모델 번호 — now vs Baumuster

SAM 파일마다 번호가 두 개 존재하며 둘 다 보존합니다.

이름출처의미
model_baumuster본문 Vehicle type원본/구형 번호 (예: 2663 LSDNA)
model_now파일 제목수정/현행 번호 — 표시 우선

본문에서 Baumuster(5자리+) 공장코드와 Subcategory도 추출해 매칭 보조 신호로 씁니다.

5.4 모델 정규화 normalize_model()

매칭 키를 만들기 위해 축 정보(8x4)·DNA·비영숫자를 제거하고 대문자화합니다.

'2851 LS' / '2851LS 6x2'  →  '2851LS'

설계 의도: 과거→현행 번호를 추측 변환하지 않습니다. 각 SAM 파일이 자기 번호(제목=now, 본문=baumuster)를 스스로 들고 있으므로, 추측 맵 대신 실제 번호로 매칭합니다. 같은 엔트리를 now·baumuster 두 키 모두에 색인해 WINGS가 어느 번호로 와도 찾히게 합니다. 값이 리스트인 이유는 두 파일이 같은 키를 공유할 수 있어 Baumuster/Subcategory로 뒤에서 구분하기 때문입니다.

5.5 SAM측 PTO 판정 & 별칭

PTO 여부는 (1) 코드 설명에 PTO 포함, (2) 본문에 \bPTO\b, (3) 파일명에 PTO — 셋 중 하나면 True. 폴더 로드 후에는 reverse_aliases 규칙으로 구형 번호 엔트리에 신형 번호 별칭 키를 자동 추가해 WINGS(신형 번호)가 SAM(구형 번호)을 찾게 합니다.

6. 비교(compare) 로직 backend/compare.py

이 시스템의 심장부입니다. WINGS 각 행마다 대응 SAM을 찾아 차이를 계산합니다. 아래 6단계로 나눠 설명합니다.

6.1 ① 모델 매칭 — 생산월 근접 + Cab 신호

SAM 맵은 월별로 여러 개일 수 있습니다(--all-months 시). 차량의 생산 요청일(Requested delivery date)에 가장 가까운 월부터 후보를 찾습니다.

prod_yyyymm = 생산일의 YYYYMM
월 목록을 |ym - prod_yyyymm| 오름차순으로 정렬 → 가까운 달부터 탐색

Cab 신호가 월 근접을 이긴다

단순히 가장 가까운 달이 아니라, 캡(cab) 종류가 맞는 후보를 우선합니다.

  • WINGS의 cab 코드(예: F1J)를 code/cab.xlsx로 변형명(예: G5F)으로 변환
  • SAM 문서의 코드에서 같은 방식으로 뽑은 변형명이 일치하면 강한 매칭. SAM 코드에 cab 코드가 하나도 없을 때만 파일 제목의 cab 토큰을 봅니다
  • 예: 한 달 떨어진 GigaSpace 파일이, 같은 달의 StreamSpace 파일보다 더 정확한 비교 대상

탐색은 가까운 달부터 돌며, cab 신호가 있으면 cab이 맞는 첫 달에서 멈춥니다. 어느 달에도 cab 매칭이 없으면 후보가 있는 가장 가까운 달로 폴백합니다.

후보 점수화 _match_score

한 엔트리에 후보가 여럿이면 점수가 가장 높은 하나를 _pick으로 고릅니다.

신호가중치
Cab 변형명 일치(SAM 코드 우선, 없으면 제목)+3
Baumuster(공장코드) 일치+2
Subcategory 일치+1

모델 키가 정확히 없을 땐 _split_model로 숫자부/접미부를 나눠 유사 키까지 탐색합니다.

수동 오버라이드는 없앴습니다

예전에는 수동매핑·매칭_별칭(수동) 시트로 특정 WINGS 모델을 특정 SAM 파일에 강제로 붙일 수 있었지만, 지금은 SAM 문서가 두 번호(제목=SAM now, 본문=SAM Baumuster)와 캡·PTO 코드를 직접 들고 있어 손으로 지정할 것이 남지 않아 두 시트를 폐기했습니다. 매칭이 틀리면 SAM 문서나 cab.xlsx 쪽 데이터를 고치세요.

6.2 ② PTO 판정 & 정교화

1차 PTO 판정: WINGS 코드 중 설명에 PTO가 들어간 코드가 있거나 WINGS_has_pto가 참이면 PTO.

정교화: 처음엔 non-PTO로 봤는데, 매칭된 SAM 엔트리에 PTO·non-PTO 두 변형이 모두 있고 WINGS 코드가 PTO 변형에만 있는 고유 코드를 포함하면 → PTO로 승격합니다.

pto_unique = PTO변형코드 - nonPTO변형코드
if wings_codes & pto_unique:  is_pto = True

PTO는 엄격 필터

확정된 PTO 여부와 같은 변형만 후보로 씁니다. 반대 변형으로 넘어가지 않으므로, 그 변형이 어느 달에도 없으면 그 차량은 No SAM이 됩니다. (예전에는 반대 변형으로 조용히 폴백해 PTO 차량이 비PTO 문서와 비교되곤 했습니다.)

6.3 ③ 코드 차이 분류

매칭된 SAM 코드집합과 WINGS 코드집합을 비교해 세 갈래로 나눕니다. 단, Factory Control 코드와 Mandatory 코드는 일반 차이에서 제외합니다(각자 별도 처리).

결과 필드정의
Only_in_SAMSAM엔 있고 WINGS엔 없음 (FC·필수 제외)
Only_in_WINGSWINGS엔 있고 SAM엔 없음 (FC·필수 제외)
Factory Control Codes양쪽 차이 중 FC(예외) 코드만 모음

FC 판정 _is_fc: 예외 집합에 있거나 접두가 I/O/Z/U. 기본 예외집합 = 접두 I/O/Z/U 코드 + DUP0, A0B, E0D, E0Q, J7G. SAM 파일을 못 찾은 행은 Only_in_WINGS를 비워둡니다(비교 불가이므로 "누락"으로 오인 방지).

6.4 ④ 필수코드(Mandatory) 검사 — 카테고리 + 그룹

필수코드는 code/mandatory-codes.xlsx가 원본입니다. 두 가지 정교한 규칙이 있습니다.

(a) 차종 카테고리 한정

코드마다 적용 차종(all/tractor/rigid/tipper)이 지정됩니다. 차량의 Baumuster 6자리로 차종을 판별(model-category.xlsx)하고, all이거나 차종이 일치할 때만 그 코드를 강제합니다. 차종을 모르면 all 코드만 적용(예: tipper 전용 코드를 미분류 차량에 잘못 표시하지 않음).

(b) "one-of" 그룹

같은 그룹명을 가진 코드들은 하나만 있으면 충족입니다(예: AEBS = S1P/S1W/S2D/S2N 중 하나). 그룹 내 변형 교체는 누락이 아닙니다. 그룹 코드는 양쪽의 그룹 보유 여부가 다를 때만 플래그됩니다.

대칭차(symmetric diff) 중:
  · 비그룹 필수코드 → 한쪽에만 있으면 즉시 누락
  · 그룹 필수코드   → 그룹을 SAM/WINGS 중 한쪽만 가질 때만 누락

6.5 ⑤ Paint / Tyre (CTT) — 별도 비교

도장·타이어는 3~4자 옵션 코드와 분리해 비교하고, 상세창 상단에 별도 섹션으로 보여줍니다.

불일치 판정 조건(오탐 방지): SAM 파일이 매칭됐고, 양쪽 모두 해당 항목을 보유하며, 집합이 서로 다를 때만 mismatch로 셉니다. 한쪽이 단순히 섹션을 누락한 경우는 불일치로 치지 않습니다.

paint_mismatch = sam_data and wings_paint and sam_paint and (wings_paint ^ sam_paint)

6.6 ⑥ 부가 정보 & 상태 결정

차종·축은 문서에 따로 없어 SAM 파일명에서 정규식으로 뽑습니다. 캡·PTO는 양쪽의 실제 코드로 판정하고(캡=cab.xlsx 변형명, PTO=설명에 PTO가 든 코드), SAM 코드에 신호가 없을 때만 파일명을 폴백으로 씁니다. 두 값은 _cab_wings/_cab_sam, _pto_wings/_pto_sam 로 모두 남겨 화면(대시보드 목록·생산월 비교·모델 매칭)에서 불일치를 ≠로 표시합니다. 목록 칸에는 WINGS 값을, WINGS에 신호가 없으면 SAM 값을 보여줍니다.

if not sam_file:                              → "No SAM"
elif Only_in_SAM/WINGS 있음 or Paint/Tyre 불일치 → "Mismatch"
else:                                          → "Match"

Changeability D-Day: Vehicle alterable until 날짜에서 오늘까지 남은 일수를 계산. done/passed는 "Passed"로 표기.

compare가 만드는 주요 출력 컬럼

Commission no., Vehicle, Model(WINGS), Type(축), Cab, PTO, SAM Baumuster, SAM now, Only_in_SAM, Only_in_WINGS, Factory Control Codes, Mandatory Codes, Changeability Date, Until Dealine, _all_wings_codes/_all_sam_codes(전체목록), _cab_wings/_cab_sam, _pto_wings/_pto_sam(양쪽 캡·PTO), _paint_*/_tyre_*, Compared SAM file name, SAM Status. (_ 접두 컬럼은 상세창 전용 원본 데이터.)

상단 ⟳ 데이터 빌드는 서버를 부르지 않습니다. 로그인한 관리자의 위임 Graph 권한으로 SharePoint를 읽어 그 브라우저에서 파이프라인을 돌리고, 결과를 다시 SharePoint에 저장합니다.

자주 겪는 상황

Q. 특정 차량이 계속 잘못된 SAM 파일과 비교돼요.

모델 매칭 화면의 매칭 결과 표에서 그 모델이 어떤 SAM 파일에 붙었는지 먼저 확인하세요. 캡이 다르면 cab.xlsx의 코드→변형명 행을, PTO가 다르면 SAM 문서의 PTO 코드/제목을 점검합니다. (수동 지정 시트는 폐기했습니다.)

Q. 멀쩡한데 "누락"으로 뜨는 코드가 있어요.

예외라면 Factory Control(접두 I/O/Z/U 또는 예외집합)에 해당하는지 확인. 필수코드 그룹(one-of) 변형이면 그룹 설정을 mandatory-codes.xlsx에서 점검하세요.

Q. 새 모델이 미분류(차종 공란)로 나와요.

Q. 빌드가 실패해요.

대부분 SharePoint 권한 또는 폴더/파일명 문제입니다. 참조 워크북이 깨져도 빌드는 폴백으로 진행되지만, 소스(WINGS/SAM) 자체가 없으면 실패합니다. 화면 우측 하단 빌드 로그 패널의 [ref]·[wings]·[sam]·[build] 라인과, 필요하면 브라우저 개발자도구 콘솔을 확인하세요.

로컬에서 실행 (개발자)

pip install -r requirements.txt

# 로컬 폴더(sam_files/ · wings_data/ · code/ · model_rules/)로 빌드
python backend/build_data.py

# WINGS 파일 지정
python backend/build_data.py --wings path/to/wings.xlsx

# 전체 생산월 비교
python backend/build_data.py --all-months

# option_codes.py 수정 시 브라우저용 사본 갱신
python backend/build_option_codes_json.py

# 결과 확인
python -m http.server -d docs 8000   # → http://localhost:8000

이 매뉴얼은 저장소의 코드 (backend/, docs/, docs/lib/)에서 직접 도출되었습니다. 로직이 바뀌면 해당 절을 함께 갱신하세요. 파일 위치는 각 절의 파일 뱃지를 참고하세요.
